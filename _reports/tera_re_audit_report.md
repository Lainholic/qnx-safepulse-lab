## 2. 치명적 발견 사항

아래 근거는 제공 본문의 **파일, 함수, 정확한 코드 구절**을 기준으로 표시합니다. 원본 파일의 실제 행 번호는 확인할 수 없어 임의로 부여하지 않았습니다.

### F-01. 무패킷 감시가 실행되지 않으며 10ms FTTI와 양립하지 않음

**심각도: 치명적**

- `safe_state_fsm.c`, `safe_state_fsm_check_starvation()`에는 `STARVATION_LIMIT_NS`와 비교해 E-STOP을 강제하는 코드가 있습니다.
- 그러나 `safepulse_resmgr.c`, `main()`의 이벤트 루프는 `dispatch_block(ctp)`와 `dispatch_handler(ctp)`만 수행합니다. 제공된 리소스 매니저 코드에는 `safe_state_fsm_check_starvation()` 호출이나 주기 타이머가 없습니다.
- 감시 함수는 `last_packet_timestamp_ns == 0`이면 즉시 반환하므로, 설령 호출하더라도 **시작 후 첫 패킷이 전혀 오지 않는 경우**는 감지하지 못합니다.
- 임계값은 **15ms**인데 명세상의 FTTI는 **10ms**입니다. 15ms에 탐지한 다음 제동 명령 전달과 실제 액추에이터 응답까지 더하면 10ms 안전 목표를 충족할 수 없습니다.
- `safe_state_fsm_step()`의 10ms 검사는 새 위반 패킷이 들어왔을 때만 수행됩니다. 패킷이 끊긴 동안에는 작동하지 않습니다.

**판정:** “패킷 침묵 시 즉시 E-STOP” 및 “10ms FTTI 보장” 주장은 코드상 성립하지 않습니다.

**권고:** 독립적인 단조 시계 기반 타이머와 시작 시각을 두고, ECU·신호별 유효 패킷 갱신을 감시하십시오. 센서 단절 탐지, 스케줄 지연, 출력 전달, 액추에이터 응답의 최악 시간 합이 검증된 FTTI 이내인지 증명해야 합니다. 프로세스 자체가 멈추는 경우에는 해당 프로세스 내부 타이머만으로 충분하지 않습니다.

### F-02. LIMP_HOME 래치가 후속 중대 결함의 E-STOP 전이를 차단함

**심각도: 치명적**

`safe_state_fsm.c`, `safe_state_fsm_step()`은 무결성 검사 직후 다음과 같이 반환합니다.

```c
if (fsm->is_latched) {
    return fsm->current_state;
}
```

이 반환은 CRC·타당성 중대 결함 검사와 10ms 경과 검사보다 앞에 있습니다. 따라서 LIMP_HOME에서 래치된 후에는 정상 패킷뿐 아니라 **새 CRC 손상, 타당성 오류, 지속 위반도 이 함수에서 E-STOP으로 격상하지 못합니다.** 별도 starvation 함수나 외부 강제 호출은 예외가 될 수 있으나, 현재 리소스 매니저에는 그 호출이 없습니다.

**권고:** 래치는 **낮은 위험 상태로의 자동 복귀를 금지**하되, 더 높은 위험 대응 상태로의 격상은 허용하도록 설계하십시오. 정상 → DEGRADED → LIMP_HOME 이후 중대 결함, 지속 결함, 시간 경과의 각 전이 시험이 필요합니다.

### F-03. 영속 래치는 크래시 일관성 및 무결성을 보장하지 못함

**심각도: 치명적**

- `safepulse_resmgr.c`, `safepulse_io_write()`는 FSM 전이 후 `persistent_fsm_state`, `persistent_fsm_latched`, `persistent_latch_time`을 각각 `memory_order_relaxed`로 저장합니다.
- 프로세스가 FSM 전이 직후 또는 이 세 저장 사이에 종료되면, 재시작 시 **이전 래치 값 또는 서로 다른 시점의 조합**을 읽을 수 있습니다. 개별 원자성은 세 필드 전체의 트랜잭션 일관성을 뜻하지 않습니다.
- `ringbuffer.h`에는 `persistent_crc32`가 있지만, 제공된 리소스 매니저의 저장·복원 경로에서 계산하거나 검증하지 않습니다.
- 재시작 시 `prev_latched`가 0이거나 `prev_state`가 범위를 벗어나면 `safe_state_fsm_init()`으로 **NORMAL 초기화**합니다. 반대로 `prev_latched != 0`이고 상태가 0 또는 1이어도 복원 조건을 통과합니다.
- 최초 SHM 생성 직후 초기화 전 크래시, 기존 SHM의 크기·버전 불일치, 손상, 재부팅 및 전원 차단에 대한 안전 정책도 제공 코드에서 확인되지 않습니다. POSIX 공유 메모리의 프로세스 종료 생존은 비휘발성 영속성과 다릅니다.

**판정:** “크래시 후 기존 안전 상태 100% 복원”은 입증되지 않았으며, 특정 크래시 지점에서는 성립하지 않습니다.

**권고:** 일관된 커밋 프로토콜과 버전·무결성 검사, 상태/래치 조합 검증을 설계하고, 불완전하거나 손상된 기록은 안전 상태로 처리하십시오. 각 저장 지점 전후에 강제 종료하는 시험과 재부팅·SHM 손상 시험이 필요합니다. 안전 출력은 복구가 끝날 때까지 독립적으로 유지되어야 합니다.

### F-04. E-STOP 상태가 실제 조향·스로틀·제동 명령을 보장하지 않음

**심각도: 치명적**

- `safe_state_fsm.c`, `safe_state_get_limits()`는 E-STOP의 `min_brake_bar = 100.0`을 반환합니다.
- 하지만 `safepulse_resmgr.c`, `safepulse_io_write()`는 비정상 상태에서 **조향과 스로틀 패킷만** 처리합니다. 제동 패킷에 최소 제동 압력을 적용하는 분기가 없습니다.
- 출력은 패킷 수신 시에만 수정됩니다. 해당 채널 패킷이 더 이상 들어오지 않으면 새로운 안전 명령을 만들어 전달하는 경로는 제공 코드에서 보이지 않습니다.
- 링 버퍼에 수정된 텔레메트리를 넣는 것과 차량 액추에이터가 명령을 수신·실행·피드백 확인하는 것은 다릅니다.

**판정:** “스로틀 0%, 조향 중심, 제동 100bar를 실제 차량에 보장한다”는 주장은 검증되지 않았습니다. 또한 고정 중심 조향과 최대 제동이 모든 주행 상황에서 안전한지는 차량 수준 위험 분석 없이 판단할 수 없습니다.

## 3. 추가 코드 및 아키텍처 평가

### 3.1 슬루 제한과 비정상 값 처리

**확인된 개선:** `actuator_slew_state_t`에 조향·스로틀·제동용 타임스탬프가 분리되어 있고, 조향·스로틀 함수의 램프 계산 후 정적 상한 재적용 코드가 있습니다.

**잔여 결함:**

1. `actuator_slew_clamp_steering()`과 `actuator_slew_clamp_throttle()`은 `timestamp_ns <= last_*_timestamp_ns`일 때 목표값을 바로 반환합니다. **동일 타임스탬프나 역행 타임스탬프에서 같은 채널의 슬루 제한이 우회**됩니다. 채널 분리만으로 이 경우가 해결되지는 않습니다.
2. `!isfinite(target_...)`를 0으로 바꾼 뒤에도 기존 출력에서 0까지 슬루 램프를 적용합니다. 이전 출력이 0이 아니고 양의 시간 간격이 있으면 **즉시 0이 아닐 수 있습니다.**
3. `safepulse_io_write()`는 `cur_state != ASIL_STATE_NORMAL`일 때만 클램프를 호출합니다. 따라서 NORMAL에서 비유한 입력이 안전하게 처리되는지는 제공되지 않은 `linter_inspect_packet()` 구현에 의존하며 확인할 수 없습니다.
4. `max_angle_limit`, `max_throttle_limit`의 유한성·음수 여부와 내부 이전 값의 무결성을 검사하지 않습니다.
5. 정적 상한이 급격히 낮아지면 최종 클램프는 상한을 우선하므로 **슬루율을 초과하는 불연속 출력**이 가능합니다. 이는 반드시 잘못이라는 뜻은 아니지만, 안전 한계와 승차감·물리적 변화율이 충돌할 때 어느 쪽을 우선하는지 안전 요구사항으로 명시해야 합니다.
6. 제동 슬루 상태와 상수는 있으나 제공 파일에 제동 슬루 함수 및 적용 경로는 없습니다.

### 3.2 시간 기준과 감시 범위

`safe_state_fsm_step()`은 수신 패킷의 `pkt.timestamp_ns`를 heartbeat와 FTTI 계산에 사용합니다. 이 값의 신뢰성, 시계 동기화, 단조성은 제공 코드에서 확인되지 않습니다. `timestamp_ns - state_entered_ns`는 부호 없는 계산이므로 시간 역행 시 큰 값으로 래핑될 수 있습니다.

또한 heartbeat가 FSM 전체에 하나뿐입니다. 조향 패킷이 계속 도착하면 제동 또는 스로틀 채널의 단절을 가릴 수 있습니다. **수신 시각과 송신 시각을 구분하고, 안전 관련 신호별 감시가 필요합니다.**

### 3.3 링 버퍼와 데이터 무손실

- `safepulse_io_write()`는 `ringbuffer_push(g_rb, &pkt)`의 반환값을 무시하고 쓰기 성공을 반환합니다. 버퍼가 가득 차서 push가 실패할 수 있다는 API 자체의 존재와 맞물려, 호출자에게 손실이 전달되지 않을 가능성이 있습니다.
- `DCMD_SAFEPULSE_SYNC_EDGE`는 `g_rb->tail = g_rb->head`를 수행합니다. 처리되지 않은 항목이 있으면 논리적으로 건너뛰게 됩니다. 명세의 “zero-latency synchronization” 및 무손실 주장과 별도로 이 동작의 목적과 허용 조건을 검증해야 합니다.
- `ringbuffer.c`가 제공되지 않아 SPSC 소유권, 메모리 순서, 슬롯 커밋, 크래시 중 push/pop 일관성은 판정할 수 없습니다. `atomic_thread_fence()` 하나만으로 전체 큐의 올바름이나 모든 플랫폼에서의 lock-free 동작이 증명되지는 않습니다.
- 패킷을 클램프한 뒤 `crc32`를 재계산하는 코드는 해당 함수에서 보이지 않습니다. CRC가 수정된 필드를 덮는다면 출력 패킷의 CRC 정합성이 깨질 수 있으므로, 실제 CRC 검증·갱신 계약을 확인해야 합니다.

### 3.4 공유 객체 접근과 결함 주입

리소스 매니저 장치와 공유 메모리는 각각 `0666`으로 생성됩니다. `safepulse_io_write()`에는 크래시 유발 명령이 있고, 제공된 분기에서는 `chaos_command_t.checksum` 검사나 호출자 권한 검사가 보이지 않습니다. 접근 제어는 시스템의 추가 보안 설정에도 좌우되지만, **제공 코드만으로는 비인가 결함 주입과 공유 안전 상태 변조를 배제할 수 없습니다.**

양산용 빌드에서 결함 주입을 분리하고, QNX 권한·접근 제어·공유 메모리 보호 및 감사 정책을 검증해야 합니다. 또한 `g_stats` 필드를 원자 타입 포인터로 캐스팅하는 코드의 적법성은 실제 `safepulse_stats_t` 선언과 모든 접근 방식을 함께 검토해야 하므로 현재 확정할 수 없습니다.

## 4. 워처와 복구 측정 평가

**개선점:** `safepulse_watcher.c`, `wait_for_device_ready()`는 재기동 후 장치 `open()` 성공을 기다리므로, 단순 spawn 시점보다 더 나은 관측 종점입니다.

다만 다음 제한이 있습니다.

1. **시작 시점:** `last_crash_time_ns = get_time_ns()`는 `waitpid()`가 반환된 뒤 실행됩니다. 실제 프로세스 사망 시각부터 워처가 관측할 때까지의 지연은 측정에서 빠집니다. 따라서 현재 지표는 엄밀히 **워처의 종료 관측 후 open 성공까지의 시간**입니다.
2. **준비성:** `open()` 성공은 해당 경로가 열렸음을 보여줄 뿐, 새 자식 프로세스가 올바른 상태를 복원했는지, 안전한 read/write·devctl을 처리하는지 증명하지 않습니다. 장치 소유자 식별과 기능적 상태 질의가 필요합니다.
3. **타임아웃:** `elapsed_us`는 `usleep(500)` 호출 횟수로 증가합니다. `open()` 자체의 블로킹 및 스케줄 지연은 계산에 포함되지 않으므로 200ms 실제 상한을 보장하지 않습니다.
4. **실패 처리:** 준비 실패 후에도 곧바로 `waitpid()`로 들어갑니다. 자식이 살아 있으면서 서비스를 제공하지 못하는 경우 워처가 계속 대기할 수 있습니다.
5. **플래핑 계산:** 다섯 번째 기록 직후 `oldest_crash = recent_crash_timestamps[crash_idx % MAX_CRASHES_IN_WINDOW]`는 방금 갱신한 슬롯을 가리킵니다. 따라서 선언된 “5회가 10초 이내” 조건과 다른 판정이 가능합니다.
6. **HAM:** 제공된 코드는 `posix_spawn()`과 `waitpid()`를 사용하는 자체 워처입니다. QNX **HAM API와의 실제 연동은 제공 코드에서 확인되지 않습니다.**
