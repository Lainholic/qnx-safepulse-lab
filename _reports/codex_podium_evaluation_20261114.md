**1. 입상 경쟁력: 무엇이 강하고, 어디서 감점되는가**

QNX 리소스 매니저, 네이티브 C 안전 검사, 공유메모리 상태 보존, `posix_spawn` 복구, 보안 정책, 장애 주입과 호스트 시각화를 하나의 실행 경로로 연결한 점은 경쟁력이 있습니다. QNX 플랫폼을 사용한 이유를 실제 기능으로 설명할 수 있고, 기존 실행 로그와 자동 검증 하네스도 존재합니다.

다만 최상위 자동차 임베디드 프로젝트와 비교하면 다음 차이가 큽니다.

| 심사 관점 | 현재 판단 |

| QNX 활용 깊이 | 입상 경쟁력이 있습니다. 리소스 매니저·스케줄링·보안 정책·복구 구조가 구체적입니다. |
| 장애 시연과 관찰 가능성 | 강점입니다. 다만 복구 성공과 안전 출력 유지의 증거를 구분해야 합니다. |
| 안전 요구사항과 구현의 일치 | 추가 수정이 필요합니다. 정지 판정과 제한값에 실제 불일치가 남아 있습니다. |
| 표준 적합성 | `AUTOSAR E2E Profile 1` 표기에 구현과 다른 부분이 확인됐습니다. |

**2. 1위 판정을 막는 핵심 공백**

**① 정지 인터록이 실제 정지를 입증하지 못합니다.**

SDK의 공개 reset 우회는 수정됐습니다. 하지만 검사 대상은 여전히 **실제 속도 측정값이 아닌 내부 `last_clamped_speed`**입니다. E-STOP 감속 함수는 초기 속도를 받은 다음, 이후 호출에서는 새 측정 속도를 반영하지 않고 내부 속도를 시간에 따라 감소시킵니다.

따라서 내부 계산 속도가 0에 도달해도 실제 차량이나 독립 시뮬레이션의 속도가 0인지 보장되지 않습니다. 측정값의 최신성 검사도 reset 조건에 없습니다.

게스트 reset 경로에는 별도의 공백도 남아 있습니다.

- 유효한 속도 수신 이력 없이 내부 속도 0으로 reset을 허용할 수 있습니다.
- SDK는 `>= 0.05`를 거부하지만, 게스트는 `> 0.05`를 거부하므로 경계 조건이 다릅니다.

이는 이전 수정의 효과를 부정하는 것이 아니라, **SDK 함수 통합 이후에도 남은 시스템 수준의 안전 문제**입니다. 근거: [SDK reset](/C:/AI/projects/qnx-safepulse-lab/guest/safepulse_api.c:178), [게스트 reset](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safepulse_resmgr.c:420), [E-STOP 감속 계산](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safe_state_fsm.c:410).

**② 안전 FSM과 실제 안전 출력 사이의 연결이 충분히 입증되지 않았습니다.**

현재 확인한 경로는 수신 패킷의 값을 제한한 뒤 링버퍼로 전달합니다. 브레이크 패킷이 들어오면 최소 압력을 적용하지만, **브레이크 ECU가 침묵한 상황에서 독립적으로 안전 명령을 생성하고 실제 제동을 유지하는지**는 이 경로만으로 입증되지 않습니다.

리소스 매니저가 죽어 있는 동안에도 같은 질문이 남습니다. 100ms 내 서비스 복구와 그 100ms 동안의 안전 제어 유지는 서로 다른 성과입니다.

또한 채널 watchdog은 패킷을 두 번 받은 뒤 활성화됩니다. 필수 ECU가 처음부터 한 번도 송신하지 않거나 한 번만 송신하면 해당 채널 검사가 활성화되지 않습니다. 다른 ECU가 계속 송신하는 상황에 대한 시작 허가 조건과 초기화 시간 제한이 필요합니다. 근거: [패킷별 clamp 경로](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safepulse_resmgr.c:561), [watchdog 활성화 조건](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safe_state_fsm.c:114).

**③ AUTOSAR Profile 1 표기와 구현이 일치하지 않습니다.**

현재 구현은 CRC-32와 modulo-16 counter를 사용합니다. AUTOSAR의 Profile 1은 CRC-8 기반이며 counter는 0부터 14까지 사용하고 15를 건너뜁니다. 따라서 현재 기능을 **표준 Profile 1 구현이라고 평가할 수 없습니다.** [AUTOSAR 공식 E2E 명세](https://www.autosar.org/fileadmin/standards/R18-10_R4.4.0_R1.5.0/FO/AUTOSAR_PRS_E2EProtocol.pdf)

추가로 자체 E2E CRC는 패킷 앞 40바이트를 대상으로 계산하고 counter는 이후 `reserved` 영역에 저장합니다. 외부 패킷 CRC는 counter 변조를 검출할 수 있지만, 자체 E2E 계층의 counter 보호 범위는 별도로 정리해야 합니다. 근거: [E2E 구현](/C:/AI/projects/qnx-safepulse-lab/guest/linter/autosar_e2e.c), [보호 길이](/C:/AI/projects/qnx-safepulse-lab/guest/include/safepulse.h:61).

심사위원이 표준 구현 경험자라면 이 부분은 기능 수보다 신뢰도에 더 큰 영향을 줄 수 있습니다.

**④ 요구사항·코드·성능 주장 사이에 불일치가 있습니다.**

- **LIMP_HOME:** 설명은 20 km/h인데 게스트 한도는 **30 km/h**입니다. 이전 수정으로 CLI와 게스트가 완전히 동기화됐다는 주장은 그대로 인정할 수 없습니다.
- **Slew 연속성:** 정상적인 증가 시간에서는 연속 ramp가 적용됐지만, 조향의 동일·역행 timestamp 분기는 즉시 hard clamp를 수행합니다. 제한 전환과 시간 이상이 겹치는 경우까지 연속성이 해결된 것은 아닙니다.
- **Zero-copy:** 링버퍼 push/pop에 `memcpy`가 존재합니다. 현재 구현을 종단 간 zero-copy라고 표현하면 반박받을 수 있습니다.
- **WCET:** 현재 벤치마크는 실제 리소스 매니저 경로 전체를 측정하지 않습니다. IPC, 상태 영속화, 알림, 실제 slew 처리 등을 포함한 최악 응답시간과 구분해야 합니다. p99도 최악시간 상한이 아닙니다.

근거: [LIMP_HOME 한도](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safe_state_fsm.c:215), [조향 시간 이상 처리](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safe_state_fsm.c:283), [링버퍼 복사](/C:/AI/projects/qnx-safepulse-lab/guest/resmgr/ringbuffer.c:68), [성능 측정 범위](/C:/AI/projects/qnx-safepulse-lab/guest/benchmark_wcet.c).

**3. 가장 효과가 큰 개선 3가지**

1. **실제 정지와 장애 중 안전 출력을 하나의 검증 시나리오로 닫으십시오.**  
   측정 속도·명령 속도·화면 표시 속도를 분리하고, reset에는 유효하고 최신인 측정 속도를 요구해야 합니다. 필수 ECU의 초기 미수신도 검출해야 합니다. 이후 “주행 중 브레이크 ECU 침묵 → 게이트웨이 크래시 → 복구 → reset 시도”를 독립 차량 모델이나 HIL에서 시험하십시오. 합격 기준은 FSM 표시뿐 아니라 제동 출력, 실제 감속, reset 거부까지 포함해야 합니다.

2. **최종 커밋 하나에 빌드·회귀·복구 증거를 묶으십시오.**  
   소스 커밋, production/test 구분, 바이너리·IFS 해시, 경고 0개 빌드 로그, 단위 테스트, secure QEMU E2E, 50회 복구 결과를 연결하십시오. 복구 시험에는 sequence 추적으로 손실·중복·순서 오류와 상태 보존을 측정하고, 최신 수정 사항을 회귀 항목으로 추가해야 합니다. 하드웨어 측정이 어렵다면 QEMU 결과의 범위를 명시하십시오.

3. **표준과 안전 요구사항의 정합성을 확보하십시오.**  
   Profile 1을 실제 명세대로 구현하고 독립 기준 벡터로 검증하거나, 현재 기능을 자체 E2E 보호 방식으로 정확히 명명하십시오. 동시에 LIMP_HOME 속도, slew와 hard limit의 우선순위, 시간 이상 처리, FTTI를 하나의 요구사항 표로 통일하고 SDK·CLI·게스트에 동일 입력을 넣어 비교하십시오. WCET와 zero-copy 표현도 실제 측정·구현 범위에 맞추십시오.

**제가 심사위원이라면 현재 작품을 입상 후보에는 올리겠지만, 단독 1위 추천은 보류하겠습니다.** 가장 큰 차이를 만드는 것은 추가 기능이나 화면 효과가 아니라, **장애 중에도 안전 동작이 유지된다는 증명과 최신 제출 버전의 재현성**입니다.
