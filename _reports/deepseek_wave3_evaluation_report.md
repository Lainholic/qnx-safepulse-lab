# SafePulse Lab — 냉정한 안전 감사 및 심사 평가

**대상:** `feat/demo-hardening` @ `4d5ad4e`
**평가 관점:** BlackBerry QNX Global Hackathon 2026 수상 경쟁력 + ISO 26262 워크프로덕트 정합성

---

## 1. [Podium / 1st Place Reality Check]

**결론: 수상권 진입은 가능하나, "Grand Prize 확정" 수준은 아니다. 상위 10~20% 후보이나 1위는 별도 조건이 필요하다.**

### 강점 (실제로 심사위원이 점수를 줄 지점)
- **QNX 고유 기능의 실사용**: `ThreadCtl(_NTO_TCTL_RUNMASK)`, `mlockall`, `SCHED_FIFO` 조합은 QNX 실습 경험이 있는 심사위원에게 "이 사람은 타깃 OS를 이해한다"는 신호를 준다. 대다수 해커톤 제출물은 Linux 사고방식으로 QNX를 쓰는 경우가 많다.
- **정량 지표 제시**: WCET 255us / FTTI 10ms(2.55%), p99.99 10.375us, SPFM/LFM/PMHF 수치. "측정했다"는 사실 자체가 상위권 차별점이다.
- **워크프로덕트 구조화**: FMEDA, MC/DC 매트릭스, HIL 시나리오를 문서로 남긴 것은 대부분의 해커톤 제출물(데모 영상 + README)보다 성숙하다.

### 냉정한 현실 (1위를 막는 요인)
- **"ASIL-D"라는 라벨의 무게**: 실제 1위를 노리는 팀들은 대개 (a) 실 하드웨어 보드에서의 데모, (b) QNX 공식 파트너/멘토의 검증 코멘트, (c) 안전 케이스(safety case)의 논리적 완결성 중 최소 2개를 갖춘다. 본 제출물은 QEMU + 에뮬레이터 기반이므로 "실증" 축에서 감점된다.
- **혁신성 축의 약함**: "zero-copy gateway + slew clamp + telemetry"는 자동차 업계에서 새롭지 않다. 심사위원이 "이게 왜 2026년에 새로운가?"라고 물으면 방어가 어렵다. 차별화 포인트(예: microkernel recovery의 결정론적 복구 시간, fail-operational 전이 로직)를 더 전면에 내세워야 한다.
- **데모 임팩트**: 1위 팀은 보통 90초 안에 "와"를 만든다. 현재 서술은 엔지니어링적으로는 훌륭하나 시각적/서사적 임팩트가 약하다.

**판정:** Podium(3위권) 가능성은 실재한다. 1위는 "실 하드웨어 1개 + 안전 케이스 1장 + 90초 데모"가 추가될 때 현실적이다.

## 2. [Exaggeration & Fluff Detection]

아래 표현들은 **반드시 톤다운 또는 재서술**해야 한다. 심사위원이 이 문구를 잡으면 신뢰도가 급락한다.

| 현재 표현 | 문제 | 권장 표현 |
|---|---|---|
| "ASIL-D Zero-Copy Safety Gateway" | ASIL-D는 **프로세스/아이템 인증 등급**이지 코드 속성 라벨이 아니다. 인증 없이 붙이면 과장. | "ASIL-D **지향** 아키텍처 프로토타입" 또는 "ASIL-D **목표**로 설계된 프로토타입 (미인증)" |
| "ISO 26262 certified" (있다면) | 인증기관 심사 없음. | "ISO 26262 Part 5/6 **워크프로덕트 형식으로 작성된** 자체 평가" |
| "Zero-Copy" | 경계를 명확히 해야 함. 커널↔유저, CAN HAL↔앱, DMA 버퍼 간 어디까지 zero-copy인지. 실제로는 특정 경로만 zero-copy일 가능성이 높다. | "**지정된 데이터 경로에 한해** zero-copy (경계: X→Y 구간)" |
| "Fail-safe" vs "Fail-operational" | 혼용 금지. Slew clamping은 fail-safe(안전 정지)에 가깝고, microkernel recovery는 fail-operational 주장에 가깝다. 둘을 같은 문장에 쓰면 모순. | 기능별로 명시: "Actuator 경로는 fail-safe, Gateway 경로는 제한적 fail-operational" |
| "Resilient Microkernel Recovery" | 복구 시간/성공률/트리거 조건이 정량화되지 않으면 마케팅 문구. | "**측정된** 복구 시간 X ms (조건: Y)" |
| "100% MC/DC Coverage" | 15/15 테스트 케이스 통과 ≠ 100% MC/DC. MC/DC는 **결정(decision) 단위** 커버리지이며, 테스트 케이스 수와 동일하지 않다. | "15개 결정에 대한 MC/DC 매트릭스 100% 충족 (대상 함수 한정)" |
| "SPFM = 99.42%, LFM = 95.80%, PMHF = 3.82 FIT" | 이 수치는 **입력 가정(진단 커버리지, failure mode 분포)**에 전적으로 의존한다. 가정을 명시하지 않으면 수치는 무의미. | "가정 기반 추정치 (가정: 부록 A), 실리콘 데이터 미반영" |
| "Physical bus-off recovery in 12.8ms" | 에뮬레이터 상의 수치. ISO 11898-1의 128×11 recessive는 **최소 시간**이며, 실제 트랜시버/클럭 편차에 따라 달라진다. | "**에뮬레이터 환경에서** 12.8ms (실 트랜시버 미검증)" |
| "3,196 pkts/s 100% overload PASS" | "PASS"의 정의가 무엇인지(드롭 0? 지연 한계?) 명시 필요. | "3,196 pkts/s에서 드롭 0 / 최대 지연 X us (정의: Y)" |

**핵심 원칙:** 모든 정량 수치 옆에 **(환경, 가정, 경계)**을 붙여라. 이게 안전 엔지니어링의 문법이다.

## 3. [Remaining Technical Boundaries — 반드시 투명하게 공개할 것]

심사위원 앞에서 **먼저 말하는 것이 유리하다**. 숨기면 감점, 먼저 밝히면 "이해도 높음"으로 가점.

1. **QEMU vs 실리콘**: WCET 255us는 QEMU 상의 수치다. QEMU는 캐시/메모리 지연/인터럽트 지터를 실제와 다르게 모델링한다. 실 보드에서 WCET는 **수 배 증가 가능**. "QEMU 측정치이며 실 보드 검증은 미수행"을 명시.
2. **에뮬레이터 CAN vs 물리 트랜시버**: M_CAN/FlexCAN 레지스터 에뮬레이션은 프로토콜 로직만 검증한다. **물리 계층(트랜시버, 종단저항, EMI, 접지 루프, 클럭 편차)**은 미검증. Bus-off 12.8ms는 물리 계층에서 재현되지 않을 수 있다.
3. **HIL 시뮬레이터의 성격**: `hil_bench_simulator.py`는 **소프트웨어 시뮬레이터**이지 HIL(하드웨어 인 더 루프)이 아니다. "HIL"이라는 명칭은 오해를 부른다. "SW-in-the-loop bench simulator"로 개칭 권장.
4. **FMEDA 입력 가정**: 진단 커버리지(DC), failure mode 분포, FIT 기저값의 출처를 명시. 실리콘 데이터시트 미반영이면 "아키텍처 수준 추정"으로 한정.
5. **MC/DC 범위**: 15개 결정이 **전체 코드의 몇 %**인지 명시. "대상 함수 한정 100%"와 "전체 코드 100%"는 하늘과 땅 차이.
6. **Zero-copy 경계**: 어느 버퍼가 공유되는지, 누가 소유권을 갖는지, 경계를 넘는 지점은 어디인지 다이어그램 1장으로 명시.
7. **Microkernel recovery의 트리거/복구 시간**: 어떤 fault에서 어떤 시간에 복구되는지 표로. "resilient"라는 형용사만으로는 부족.
8. **Safety case 부재**: FMEDA 수치는 safety case의 일부일 뿐. "왜 이 아키텍처가 ASIL-D 목표에 부합하는가"의 논증(argument)이 없다.

## 4. [Final Verdict — 환님께]

**종합 평가: B+ (기술적 성숙도 상위권, 실증/서사 축 보강 필요)**

### 지금 상태로 심사에 임하면
- **기술 심사**: 상위권. QNX 네이티브 기능 활용, 정량 지표, 워크프로덕트 구조는 강점.
- **수상 경쟁**: Podium 진입 가능. 1위는 불확실. 과장 문구가 발각되면 순위 하락 리스크.

### 즉시 조치 (우선순위 순)
1. **과장 문구 전수 톤다운** (섹션 2 표 기준). "ASIL-D", "certified", "zero-copy", "HIL" 네 단어를 먼저 손봐라.
2. **경계 명시 섹션 추가**: README 최상단에 "Scope & Limitations" 1페이지. QEMU/에뮬레이터/가정을 먼저 밝혀라. 이것이 방어막이다.
3. **90초 데모 스크립트**: bus-off → 복구 → slew clamp → telemetry의 서사를 시각적으로. 수치보다 "무슨 일이 일어나는가"를 보여라.
4. **실 하드웨어 1개 확보**: 가능하면 Raspberry Pi + MCP2515 또는 QNX 지원 보드에서 최소 1개 시나리오 재현. "QEMU + 실 보드 1개"는 "QEMU only"와 심사에서 급이 다르다.
5. **Safety case 1장**: "왜 이 아키텍처가 ASIL-D 목표에 부합하는가"를 GSN(Goal Structuring Notation) 1페이지로. FMEDA 수치는 그 안의 evidence로.

### 냉정한 한마디
이 코드베이스는 **"엔지니어가 만든 것"**이지 **"마케터가 만든 것"**이 아니다. 그게 강점이다. 다만 지금 서술 톤은 마케터 쪽으로 기울어 있다. **수치 옆에 항상 (환경, 가정, 경계)를 붙이는 습관** 하나만으로 심사위원의 신뢰가 크게 달라진다. 과장을 걷어내면 오히려 더 강해 보인다 — 안전 엔지니어링에서는 그게 진실이다.
