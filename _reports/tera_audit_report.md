## 2. 주요 발견사항

### 2.1 FSM: 단방향 래칭과 10ms FTTI 보장 실패 — 치명

**근거:** `guest/resmgr/safe_state_fsm.c:41–117`, `guest/resmgr/safepulse_resmgr.c:80–83, 253–255`.

1. **4단계 전체의 단방향 래칭은 구현되지 않았습니다.** 정상 입력이 누적되어 `consecutive_faults == 0`이 되면 `DEGRADED → NORMAL`로 복귀합니다. 반면 제공된 함수 내에는 `LIMP_HOME`과 `EMERGENCY_STOP`에서 정상 복귀하는 경로가 없습니다. 즉 전체 단방향 래칭도 아니고, 모든 상태의 검증된 복귀 정책도 아닙니다.

2. **10ms 타이머는 독립적으로 동작하지 않습니다.** 시간 검사 자체가 `has_violation` 분기 안에 있고, FSM은 수신 패킷 처리 시 호출됩니다. 입력이 멈추거나, 이후 입력이 정상으로 판정되면 해당 검사만으로는 10ms 만료 시 안전 상태로 전환할 수 없습니다. 패킷의 `timestamp_ns`를 그대로 사용하므로 신뢰 가능한 단조 시계와의 관계도 입증되지 않았습니다.

3. **상태 진입 시각이 단계마다 갱신됩니다.** `DEGRADED → LIMP_HOME` 전환 시 `state_entered_ns`가 재설정되므로, 최초 결함부터의 경과시간을 지속적으로 제한하는 구조가 아닙니다. 따라서 “최초 결함부터 10ms 이내 E-STOP”을 보장하지 못합니다.

4. **재기동 시 래치가 사라집니다.** 공유 메모리를 다시 연결한 뒤에도 `safe_state_fsm_init(&g_fsm)`을 호출해 NORMAL로 초기화합니다. 비정상 종료 직전 E-STOP이었다 해도 그 상태를 보존하거나 안전하게 복원하는 코드는 제공된 범위에 없습니다.

5. `safe_state_fsm_step(NULL, ...)`은 NORMAL을 반환합니다. 호출자가 이를 안전 상태로 해석하면 내부 오류를 정상으로 오인할 수 있습니다.

**추가 주의:** `consecutive_faults`는 `uint32_t`이므로 장시간 증가 시 순환합니다. `safety_score`가 NaN이면 `< 70.0f` 비교가 거짓이므로 위반 코드가 0일 때 이를 결함으로 취급하지 않습니다. `timestamp_ns` 역행 시 unsigned 뺄셈이 큰 값으로 순환할 수도 있습니다.

### 2.2 액추에이터 제한: 안전 한계와 램프가 충돌 — 치명

**근거:** `guest/resmgr/safe_state_fsm.c:120–150, 164–235`; `guest/include/safe_state_fsm.h:35–43`; `guest/resmgr/safepulse_resmgr.c:83–91`.

- 목표값을 먼저 새 한계로 자른 뒤, 이전 출력에서 슬루 제한을 적용합니다. 따라서 **최종 출력은 새 정적 한계를 넘어설 수 있습니다.**
  - 예: 이전 스로틀이 100%, E-STOP 한계가 0%, 경과시간이 10ms라면 100%/s 제한의 결과는 **99%**입니다.
  - 이전 조향이 540°이고 E-STOP 목표가 0°라면 이상적인 250°/s 램프만으로 중심까지 **2.16초**가 걸립니다.
- 슬루 상태는 NORMAL 패킷 처리 중 갱신되지 않습니다. 안전 상태에 처음 진입했을 때 `last_slew_timestamp_ns == 0`이면 목표값을 즉시 반환하므로, 실제 이전 액추에이터 출력과 연속적인 램프가 보장되지 않습니다.
- 조향과 스로틀이 **동일한 `last_slew_timestamp_ns`**를 공유합니다. 두 채널에 같은 시각의 패킷이 순서대로 들어오면 두 번째 채널은 `timestamp_ns <= last_slew_timestamp_ns` 분기로 들어가 램프를 우회할 수 있습니다.
- 브레이크 150 bar/s 상수와 `last_clamped_brake`는 선언되어 있지만, 제공된 코드에는 브레이크 슬루 함수나 브레이크 패킷에 `min_brake_bar`를 적용하는 경로가 없습니다.
- NaN은 크기 비교를 통과하므로 목표값 또는 한계값의 유한성 검사가 필요합니다. NULL 슬루 포인터도 원래 목표값을 그대로 반환합니다.

**물리 적합성 판정:** 250 deg/s, 100%/s는 이 코드의 상수일 뿐, 제공 자료는 해당 수치가 차량 전복이나 jerk를 방지한다고 입증하지 않습니다. 조향각 변화율은 횡가속도·요레이트·차속·타이어 및 노면 상태와 같지 않으며, 압력 변화율도 차량 종방향 jerk와 동일하지 않습니다. ISO 26262 자체가 이 특정 수치를 보편적인 전복 방지 기준으로 정한 것처럼 표현할 근거도 제공되지 않았습니다. 또한 “조향 중심 + 100 bar”가 모든 주행 상황의 안전 상태라는 근거가 없습니다.

### 2.3 재기동과 카오스 실측: 4.2ms 및 무손실 주장 미입증 — 치명

**근거:** `guest/safepulse_watcher.c:77–91, 116–141`; `_reports/chaos_marathon_report.md:12–42`; `SUBMISSION.md:9–25`.

워처의 순서는 다음과 같습니다.

1. `waitpid()`가 반환된 뒤 `crash_time_ns` 기록
2. 백오프 후 `usleep()` 종료
3. **“Recovery complete” 출력**
4. 다음 루프에서야 `posix_spawn()`으로 새 프로세스 생성

따라서 이 코드의 `recovery_ms`는 **자식 종료 관측 후 백오프가 끝날 때까지의 시간**이며, 실제 장애 발생부터 새 프로세스가 `/dev/safepulse`를 등록하고 요청 처리 가능한 시점까지의 복구 시간이 아닙니다. 측정에는 탐지 지연, 다음 spawn 및 서비스 준비 시간이 포함되지 않습니다. 보고서의 4.2ms가 정확히 이 값에서 유래했는지 원시 자료가 없어 확정할 수는 없지만, 현재 제공된 워처 코드만으로 **4.2ms 서비스 복구**를 증명할 수 없습니다.

또한:

- 보고서의 평균 4.2ms와 최대 180ms는 `SUBMISSION.md:9`의 **sub-3ms 보장**과 양립하지 않습니다. 최대 180ms는 제시된 프로젝트 지침의 1ms 기준도 충족하지 않습니다.
- SHM이 프로세스 종료를 넘어 유지될 수 있다는 사실은 **처리 중인 패킷, 응답 전 패킷, 큐 포화 중 패킷, 재기동 중 새로 들어오는 패킷의 무손실**을 뜻하지 않습니다. 성공한 쓰기와 실제 소비 결과를 시퀀스별로 대조한 원시 증거가 필요합니다.
- `ringbuffer_push()`의 반환값을 확인하지 않고 쓰기 성공을 응답합니다. 함수가 포화나 오류를 반환하는 설계인지 구현이 없어 확인할 수 없지만, **반환값에 의존하는 실패 처리는 보이지 않습니다** (`safepulse_resmgr.c:94–95, 132–133`).
- 보고서 표의 13/13/12/12와 “Engineering Insights”의 11/8/6/4는 서로 다릅니다. 후자가 같은 50회 시험의 분포라면 합계 29회이므로 정정 또는 별도 시험이라는 설명이 필요합니다.
- 50회 모두 성공하더라도 모집단 전체의 성공률이 100%라는 통계적 증명은 아닙니다. 독립 시행이라는 가정 아래 실패율의 대략적인 95% 단측 상한은 **약 5.8%**입니다. 실제 시험의 독립성은 확인되지 않았습니다.

워처는 `posix_spawn()`과 `waitpid()`를 사용하는 **자체 감독 프로세스**로 확인됩니다. 제공 코드에 QNX HAM API 호출은 보이지 않으므로 실제 HAM 서비스 연동으로 기술할 근거는 없습니다. `SIGSEGV` 유발의 NULL 역참조와 정수 0 나누기는 C에서 정의되지 않은 동작이므로, 소스만으로 특정 신호 발생을 보장할 수도 없습니다.

### 2.4 링버퍼: fence만으로 SPSC 안전성이나 무손실 입증 불가 — 중대

**근거:** `SUBMISSION.md:87–91`; `guest/resmgr/safepulse_resmgr.c:94–95, 164–166`; 링버퍼 구현은 미제공.

`atomic_thread_fence(memory_order_release/acquire)`의 존재만으로 비원자 인덱스 접근의 데이터 레이스가 해결되거나 스레드 간 동기화가 자동으로 생기지는 않습니다. C11의 fence 동기화에는 적절한 **원자 객체를 통한 연결**이 필요하며, payload 기록·head 공개·tail 관측·슬롯 재사용 전체를 검토해야 합니다. 호출부의 `ringbuffer_push()` 뒤 release fence도 그 자체로 push 내부의 공개 순서를 증명하지 않습니다.

추가로 확인해야 할 사항은 다음과 같습니다.

- `head`, `tail`, `drop_count`의 실제 선언과 모든 접근의 원자성·메모리 순서.
- QNX의 대상 ABI에서 프로세스 간 공유되는 원자 객체의 정렬, lock-free 여부, 초기화·재연결 방식.
- 하나의 생산자와 하나의 소비자라는 불변식. 제공된 리소스 매니저는 단일 dispatch 루프이지만, 공유 메모리의 직접 접근자까지 포함한 전체 구성은 확인되지 않았습니다.
- `DCMD_SAFEPULSE_SYNC_EDGE`는 제공 코드상 `tail = head`입니다. 이는 현재 대기 중인 항목을 **논리적으로 건너뛰는 효과**가 있으며, “zero-latency synchronization”이나 무손실의 증거가 아닙니다.
- 공유 메모리 보존과 crash-consistent commit은 다릅니다. payload 기록 도중, head 공개 직전·직후, pop 중 종료되는 경우를 각각 시험해야 합니다.

`ringbuffer_pop(g_rb, &pkt)`와 `MsgReply()`는 로컬 패킷 객체를 사용합니다 (`safepulse_resmgr.c:36–39`). 따라서 최소한 이 경로의 **종단 간 zero-copy**는 제공 코드로 입증되지 않습니다.

### 2.5 AUTOSAR E2E Profile 1: 구현과 방어율 판정 불가 — 중대

**근거:** `SUBMISSION.md:56–59`; `guest/include/safepulse.h:36–54`; E2E 구현과 시험 벡터 미제공.

- 제출문은 CRC-8 생성 다항식으로 `0xF4ACFB13`을 명시하지만, 이는 **8비트 다항식 표기값이 아닙니다.** 환님이 제시한 `0x1D`와도 일치하지 않습니다. 이것만으로 실제 구현의 다항식을 확정할 수는 없습니다.
- 4비트 카운터와 CRC만으로 모든 반복·누락·지연을 검출할 수는 없습니다. 카운터는 16단계마다 순환하며, 허용 delta·초기화·재동기화·타임아웃 정책이 검출 범위를 결정합니다. 지연 검출에는 별도 시간 감시가 필요합니다.
- 16비트 Data ID 결속은 프로파일 설정에 따른 오결합 검출에 기여할 수 있지만, CRC는 암호학적 인증이 아니므로 의도적 위조 방어를 보장하지 않습니다.
- 제공된 패킷 헤더에는 CRC-32 필드가 보이지만, E2E 카운터·CRC-8·Data ID의 배치와 처리 경로는 보이지 않습니다. `reserved`의 실제 사용 여부도 확인할 수 없습니다.

**필요 증거:** 적용 AUTOSAR 릴리스·Profile 1 설정, Data ID 모드와 바이트 순서, CRC 초기값·최종 XOR·대상 범위, 카운터 상태기계, 공식 또는 독립 기준 벡터와 손상·반복·누락·순환·지연 시험 결과. 현재 **방어율은 산정 불가**입니다.

### 2.6 스케줄링과 무간섭: 설정 시도는 확인, FFI는 미입증 — 중대

**근거:** `guest/resmgr/safepulse_resmgr.c:277–307`; `SUBMISSION.md:93–99`.

코드는 `SCHED_SPORADIC` 우선순위 50/15, 초기 예산 3ms, 주기 10ms를 설정하려 시도합니다. 실패 시 FIFO 50을 시도하고, 그것도 실패하면 **상속된 우선순위로 계속 실행**합니다. 어느 정책이 실제 시험에서 적용되었는지는 로그가 없어 확인되지 않습니다.

- 명목 예산 비율은 **30%**입니다. 이것이 해당 태스크의 최악 응답시간이나 10ms 내 안전 반응을 보증하지는 않습니다.
- FIFO 폴백은 동일한 예산 격리를 제공하지 않습니다. 높은 우선순위 작업, 인터럽트, 자원 대기, CPU affinity, 메모리·캐시·공유 버스 간섭 등을 포함한 분석이 필요합니다.
- “5,000 packets, 0 misses”는 특정 시험 결과라는 주장일 뿐, 시험 하네스·워크로드·관측 정의가 없어 독립 검증되지 않았으며 일반적인 ASIL-D FFI 준수를 증명하지 않습니다.
- 평균이나 p99.9는 **WCET가 아닙니다**. `SUBMISSION.md:18`의 평균 904~938ns와 p99.9 1.77µs로 최대 실행시간을 확정할 수 없습니다. 1.75% FTTI 수치의 산식도 명확하지 않습니다.

### 2.7 C11·보안 경계 및 기타 코드 위험

**근거:** `guest/resmgr/safepulse_resmgr.c:96–103, 106–130, 146–165, 208–255`; `guest/include/safepulse.h:32–65`.

- `*(uint32_t *)&pkt.safety_score`는 float 객체를 호환되지 않는 정수 타입 lvalue로 읽는 형태로 **strict aliasing 위반 위험**이 있습니다. `memcpy` 등을 이용한 표현 복사와 수신 측 해석을 명확히 해야 합니다.
- 일반 필드를 `_Atomic uint32_t *`로 캐스팅해 접근하는 부분은 실제 필드 선언, 정렬 및 모든 접근 방식이 확인되지 않아 적합성을 증명할 수 없습니다. 통계 조회의 구조체 복사와 초기화까지 포함해 동시 접근을 검토해야 합니다. 다만 제공된 단일 dispatch 루프만으로 실제 레이스 발생을 단정할 수는 없습니다.
- `#pragma pack(1)`은 레이아웃 크기를 확인하지만 엔디언, IEEE 부동소수점 표현, 비정렬 접근의 이식성까지 보장하지 않습니다.
- 패킷은 린터 검사 이후 값이 변경됩니다. 변경된 패킷의 CRC를 다시 계산하는 코드는 호출부에 보이지 않습니다. 린터 내부 구현이 없으므로 실제 CRC 정합성은 확인이 필요합니다.
- 장치와 SHM 생성 권한이 `0666`이고, 쓰기 경로에서 치명적 결함 주입 명령을 수용합니다. 접근 제한·운영용 빌드 분리 여부는 확인되지 않습니다. 안전 기능과 결함 주입 기능의 권한 격리가 필요합니다.
- 공유 메모리 생성 후 초기화 전에 프로세스가 종료되면, 다음 실행은 기존 객체를 신뢰하고 연결할 수 있습니다. 크기·버전·초기화 완료 표시 검증은 제공 코드에 보이지 않습니다.
- `shm_fd`, 매핑 및 dispatch 자원의 정상 종료 정리가 보이지 않지만, 이것만으로 장시간 운전 중 누수량을 산정할 수는 없습니다. `mallinfo`의 0 증가 주장도 원시 측정과 범위가 없어 검증 불가입니다.
- 워처의 `waitpid()` 오류 및 `EINTR` 처리, 시그널 핸들러와 `g_child_pid` 접근, 신호 번호 하드코딩의 QNX 이식성도 별도 검토가 필요합니다.
