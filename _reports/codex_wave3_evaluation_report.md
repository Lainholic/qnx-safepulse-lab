환님, **현재 상태를 “입상 확정권”이나 “대상급으로 검증된 프로젝트”라고 판정할 수 없습니다.** QNX 리소스 매니저, 프로세스 감시·재시작, 공유메모리 상태 복구, 안전 상태 제어는 기술 심사를 받을 만한 구현입니다. 하지만 **Wave 3에서 추가한 물리 HIL, 운영 코드 MC/DC 100%, 정량 FMEDA 달성 주장은 현재 코드와 근거로 성립하지 않습니다.** 이 표현을 그대로 제출하면 기술적 깊이보다 검증 신뢰성 문제가 먼저 드러날 가능성이 큽니다.

감사 대상은 실제 `feat/demo-hardening` 브랜치의 `4d5ad4e`로 확인했습니다. 이번에는 소스·빌드 연결·기존 로그와 공식 자료를 대조했으며, QNX 빌드와 QEMU 시험을 새로 실행하지 않았습니다. 파일은 수정하지 않았습니다. 아래 평가는 공식 심사 결과가 아닌 독립적인 기술 감사 의견입니다.

**1. 입상·대상 경쟁력**

공식 심사 기준은 기술 구현, 디자인, 잠재적 영향, 혁신성·AI 창의성의 네 축입니다. 안전 용어나 시험 항목 수가 많다고 높은 순위를 보장하지 않습니다. QNX에서 실제 작동하는 구현과 함께 일관된 제품 경험, 구체적인 문제 해결 가치가 필요합니다. [대회 공식 심사 기준](https://qnx.devpost.com/rules)

| 평가 축 | 현재 판단 |
|---|---|
| 기술 구현 | QNX 고유 기능을 활용한 구현이 존재합니다. 다만 Wave 3의 HAL은 실제 서비스 경로에 연결되지 않았고, 검증 주장에 중대한 결함이 있습니다. |
| 디자인·제품 경험 | 대시보드와 결함 주입 흐름은 제품 설명에 도움이 됩니다. 이번 감사에서는 실제 화면과 전체 시연을 재검증하지 않아 완성도를 확정할 수 없습니다. |
| 잠재적 영향 | 게이트웨이 장애 격리·복구라는 문제는 구체적입니다. 실제 적용 대상, 기존 방식 대비 이점, 물리 제어 경로에 대한 증거는 부족합니다. |
| 혁신성 | 기존 안전 기법을 QNX 기반 개발·진단 도구로 통합한 가치가 있습니다. CAN HAL, CRC, slew 제한, 프로세스 재시작 자체를 새로운 자동차 안전 기술로 제시하기는 어렵습니다. |

**입상 후보가 될 가능성은 있지만, 현재 자료로 그 경쟁력을 확정할 수는 없습니다.** 경쟁작 전체를 확인하지 않은 상태에서 순위나 확률을 제시하는 것도 근거가 없습니다.

실제 보드가 없거나 ASIL 인증이 없다는 이유만으로 해커톤 대상에서 배제할 근거는 없습니다. 현재의 더 큰 문제는 **확보하지 않은 증거를 확보했다고 표현한 부분**입니다.

**2. 가장 심각한 과장과 검증 결함**

**① “물리 HIL 4개 시나리오 PASS”는 물리 검증으로 인정할 수 없습니다.**

[hil_bench_simulator.py](C:/AI/projects/qnx-safepulse-lab/host/hil/hil_bench_simulator.py:120)의 판정 방식은 다음과 같습니다.

| 주장 | 코드가 실제로 수행하는 일 | 인정 가능한 범위 |
|---|---|---|
| ±100 ppm 수정 발진기 드리프트 | Python `sleep` 주기를 무작위로 변경하고 `sendall` 호출 시간을 측정합니다. | 호스트 송신 간격 교란 실험 |
| EMI 과도 잡음 | SafePulse 패킷 CRC를 변조해 전송하고, 대상의 검출 결과 확인 없이 PASS를 설정합니다. | 손상 패킷 주입 동작 |
| bus-off 12.8 ms 복구 | Python 내부 카운터 증가, 50 ms 대기, 상수 `12.8` ms 대기 후 PASS를 설정합니다. | 복구 절차를 설명하는 모의 시나리오 |
| CAN FD 100% 과부하 | TCP로 500개 패킷을 보내고 송신률이 250 packets/s를 넘으면 PASS입니다. | 호스트 TCP 송신 처리율 측정 |

특히 bus-off 시나리오는 **게스트 HAL에 bus-off를 발생시키지도, TEC를 읽지도, 복구 완료를 관측하지도 않습니다.** 따라서 12.8 ms는 실측 복구 시간이 아닙니다.

또한 `sendall` 성공은 수신 측 처리 완료나 무손실을 입증하지 않습니다. CAN 버스 점유율에는 중재·데이터 비트율, 프레임 구성, stuffing, ACK, 재전송 등이 필요합니다. TCP packets/s를 CAN 100% 점유율로 환산할 수 없습니다.

이는 단순한 표현상의 문제가 아니라 **시험 대상과 PASS 조건이 주장에 대응하지 않는 문제**입니다.

**② CAN HAL은 현재 소프트웨어 루프백 모델이며, M_CAN/FlexCAN 레지스터 에뮬레이터라는 설명은 과합니다.**

[HAL 구현](C:/AI/projects/qnx-safepulse-lab/guest/hal/safepulse_hal_can.c:101)에서 확인한 사항입니다.

- 레지스터 맵, MMIO 접근, 인터럽트, 실제 컨트롤러 백엔드가 없습니다.
- 송신한 프레임을 동일 채널의 내부 Rx FIFO에 복사합니다.
- bus-off 복구 함수는 recessive 비트를 관측하거나 기다리지 않고 즉시 카운터를 초기화합니다.
- 설정된 비트율과 sample point로 버스 타이밍을 모델링하지 않습니다.
- `bus_load_pct`는 초기값 5.0으로 설정되며 실제 점유율 계산이 없습니다.
- CRC는 payload에 대해 계산하며, 수신 프레임의 CRC-21 오류를 검증하는 경로가 없습니다.

실제 M_CAN은 CPU의 초기화 해제와 버스 idle 관측을 포함하는 복구 동작을 정의합니다. Bosch 문서에는 129회의 11 recessive-bit 구간 대기가 설명되어 있습니다. 현재 구현은 그 동작의 에뮬레이션을 입증하지 못합니다. [Bosch bus-off 복구 설명](https://www.bosch-semiconductors.com/media/ip_modules/pdf_2/m_can/m_can_an004_v1-0_busoff_recovery_handling.pdf)

더 직접적인 문제는 [build.bat](C:/AI/projects/qnx-safepulse-lab/guest/build.bat:36)에서 `hal_can.o`를 컴파일하지만, 리소스 매니저나 브리지에 링크하지 않는다는 점입니다. 확인한 운영 코드에는 HAL API 호출도 없습니다. **HAL 파일의 존재를 실제 게이트웨이 CAN 경로 구현으로 설명할 수 없습니다.**

안전성 결함도 있습니다. `hal_can_transmit()`은 `payload_len <= 64`를 검증하지 않고 CRC 함수에 전달합니다. 잘못된 길이로 payload 배열 밖을 읽을 수 있습니다.

**③ “운영 안전 로직 MC/DC 100%”는 입증되지 않았습니다.**

[test_mcdc_matrix.c](C:/AI/projects/qnx-safepulse-lab/guest/test_mcdc_matrix.c:60)는 실제 린터·FSM·slew 함수를 호출하는 대신 `eval_decision_1`부터 `eval_decision_4`까지 별도 작성한 논리식을 시험합니다.

따라서 15/15 PASS가 의미하는 것은 **선정한 네 개의 예제 논리식이 예상 결과를 냈다**는 것입니다. 운영 코드 전체의 조건·결정 커버리지를 의미하지 않습니다.

FSM은 복제한 논리식과 실제 구현도 다릅니다. 시험은 다음을 평가합니다.

`is_critical || (degraded_held && err_count >= 5)`

반면 [실제 FSM](C:/AI/projects/qnx-safepulse-lab/guest/resmgr/safe_state_fsm.c:161)은 특정 critical violation에서 즉시 E-STOP으로 전환하고, DEGRADED 유지 시간이 지나면 LIMP_HOME으로 전환합니다. 해당 운영 경로에는 시험식과 같은 다섯 번 오류 조건의 E-STOP 분기가 없습니다.

운영 소스의 결정 목록, 각 조건의 독립 영향 쌍, 실제 실행 추적과 커버리지 집계가 필요합니다. 현재 출력의 **`100.0% (ASIL-D Qualified)`는 근거가 없습니다.**

**④ FMEDA 수치는 “달성한 안전 지표”로 사용할 수 없습니다.**

[FMEDA 문서](C:/AI/projects/qnx-safepulse-lab/_reports/iso26262_fmeda_and_metrics.md:23)에는 총 100 FIT, 진단 커버리지 95~99.9%, SPFM 99.42%, LFM 95.80%, PMHF 3.82 FIT가 제시됩니다. 하지만 다음 근거가 빠져 있습니다.

- 실제 대상 하드웨어와 부품별 고장률 출처
- 사용 온도·운용 환경·mission profile
- 고장 모드별 안전·단일점·잔여·다중점 고장 분류
- 진단 커버리지의 산정·검증 근거
- latent fault 검출 주기와 다중점 고장 계산
- 표의 입력에서 최종 세 수치로 이어지는 재현 가능한 계산

소프트웨어 프로세스 crash, 외부 EMI 현상, 하드웨어 부품 고장을 하나의 랜덤 하드웨어 고장률 표에 함께 넣은 분류도 재검토해야 합니다.

SPFM·LFM·PMHF 목표값이 알려져 있다는 사실과 프로젝트가 그 값을 충족했다는 증명은 다릅니다. 반도체 업체의 FMEDA도 고장률과 진단 효과를 정량화하는 근거 자료를 전제로 합니다. [TI 기능 안전 분석 설명](https://www.ti.com/document-viewer/lit/html/sszt066)

**현재 문서는 가정을 사용한 FMEDA 초안으로 볼 수 있으며, ASIL-D 정량 안전 지표 충족 증거로는 인정하기 어렵습니다.**

**⑤ 255.043 μs는 기록된 관측 최대값이며, 보장된 WCET가 아닙니다.**

기존 [qemu_live.log](C:/AI/projects/qnx-safepulse-lab/_reports/qemu_live.log:107)에 `255.043 μs`가 기록된 것은 확인했습니다. 수치 자체를 만들어 낸 것으로 판단하지 않습니다. 다만 그 의미는 제한해야 합니다.

[벤치마크](C:/AI/projects/qnx-safepulse-lab/guest/benchmark_wcet.c:39)에서는 다음 문제가 있습니다.

- `ThreadCtl`, `mlockall`, `sched_setscheduler` 반환값을 확인하지 않습니다. 출력 문구만으로 설정 성공을 확정할 수 없습니다.
- 측정 구간은 인라인 계산 경로이며 IPC 대기, 큐 적체, TCP 전달, 출력 장치 반응까지 포함하지 않습니다.
- 실제 `actuator_slew_clamp_*()` 대신 제한값과 단순 비교를 수행합니다.
- 10만 회의 특정 입력·실행 환경에서 관측한 최대값으로 가능한 모든 실행의 상한을 보장할 수 없습니다.
- 게스트 CPU 고정은 호스트 스케줄링이나 QEMU 정지를 통제하지 못합니다.

255.043 μs가 10 ms의 약 2.55%라는 산술은 맞습니다. **전체 고장 검출·안전 반응이 FTTI의 2.55% 안에 끝난다는 결론은 성립하지 않습니다.**

출력의 `ASIL-D 10ms FTTI Determinism Certified`는 삭제해야 할 인증 표현입니다.

| **Fail-operational / 무중단 복구** | 재시작과 상태 보존은 기능 연속 운용을 자동으로 보장하지 않습니다. 복구 중 서비스 공백, 대체 제어 경로, 허용된 성능 저하를 측정해야 합니다. |
| **100 bar → 실제 안전 정지** | 텔레메트리 값을 생성·제한하는 것과 브레이크 액추에이터가 압력을 형성해 차량을 정지시키는 것은 별도 증거가 필요합니다. |

심사위원에게는 다음 한계도 명시해야 합니다.

- 현재 검증 대상은 QEMU 기반 가상 ECU·게이트웨이이며, 실제 CAN 트랜시버와 차량 제어계를 검증하지 않았습니다.
- ECU·버스가 모두 침묵했을 때도 물리적으로 제동할 수 있는 독립 전원·통신·액추에이터 경로가 입증되지 않았습니다.
- 조향을 0도로 복귀시키거나 일정 제동 압력을 강제하는 정책은 속도·노면·차량 거동에 따라 위험할 수 있습니다. HARA와 차량 동역학 근거 없이 보편적 안전 상태로 확정할 수 없습니다.
- 단일 CPU·공유메모리·전원·watcher 등에 대한 공통 원인 고장과 독립성 분석이 부족합니다. 같은 프로세스의 반전 상태값은 독립된 이중 제어 채널이 아닙니다.
- 이번 감사에서는 현재 커밋의 빌드 경고 0개, 8/8 결합 시험, 50회 복구·무손실을 재실행하지 않았습니다. 과거 PASS와 현재 버전 검증은 구분해야 합니다.

**4. 최종 판정**

환님, 현재 프로젝트는 **QNX 기반 안전 텔레메트리·장애 복구 프로토타입의 개발·검증 단계**입니다. 자동차 양산 안전 게이트웨이 수준이나 ASIL-D 충족 상태로 볼 수는 없습니다.

해커톤에서는 그 수준의 인증까지 요구하지 않습니다. 따라서 경쟁력을 확보하는 데 가장 필요한 일은 안전 용어를 더 추가하는 것이 아니라, **현재 구현이 실제로 보장하는 범위를 정확하게 증명하는 것**입니다.

우선순위는 세 가지입니다.
